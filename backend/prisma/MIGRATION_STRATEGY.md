# GroceNest Database Migration Strategy & Production Runbook

This document defines the database migration policy, automated deployment pipeline, pre-migration backup procedures, emergency rollback protocols, and zero-downtime migration guidelines for GroceNest.

---

## 1. Core Principles

1. **Automation First**: Schema migrations auto-run on deployment using `npx prisma migrate deploy` via `deploy-migrations.sh`.
2. **Pre-Migration Backups**: A timestamped PostgreSQL database dump (`pg_dump`) is created automatically BEFORE any schema migration is applied.
3. **Zero-Downtime Design**: All schema alterations follow the **Expand and Contract** pattern to avoid breaking active application pods during rolling updates.
4. **Tested Migrations**: All migration files are committed to source control and verified against test databases in CI/CD before hitting production.

---

## 2. Automated Migration Pipeline (`deploy-migrations.sh`)

Migrations run automatically during deployment via `npm run db:migrate:deploy`.

### Execution Flow:
1. **Connectivity Check**: Verifies `DATABASE_URL` is configured and accessible.
2. **Automated Backup**: Executes `pg_dump` to create a timestamped SQL snapshot in `backend/backups/db_pre_migration_<TIMESTAMP>.sql`.
3. **Migration Apply**: Runs `npx prisma migrate deploy` to safely apply pending Prisma migrations in sequence.
4. **Health Audit**: Confirms database responsiveness and schema version after application.
5. **Fail-Safe Halted Rollback**: If `prisma migrate deploy` fails, deployment is aborted immediately, preserving the pre-migration snapshot for rollback.

```bash
# Manual execution or deployment hook
npm run db:migrate:deploy
```

---

## 3. Zero-Downtime Migrations (Expand and Contract Pattern)

To achieve 100% uptime during blue-green or rolling container deployments, direct breaking schema changes (e.g. dropping columns, renaming columns, adding NOT NULL fields without defaults) are **STRICTLY PROHIBITED** in a single release.

### Phased Migration Workflow

#### Example: Renaming column `phone` to `phoneNumber`

| Phase | Schema Action | Application Behavior |
| :--- | :--- | :--- |
| **Phase 1: Expand** | Add `phoneNumber String?` as an optional column alongside `phone`. | Old code reads/writes `phone`. New code dual-writes to both `phone` and `phoneNumber`. |
| **Phase 2: Backfill** | Execute background script to populate `phoneNumber` for historical rows where `phoneNumber IS NULL`. | All active instances write to `phoneNumber`. |
| **Phase 3: Contract** | Deploy updated application code using `phoneNumber` exclusively. Drop legacy `phone` column in a subsequent release. | Clean schema without downtime or field locks. |

### Rules for Schema Changes:
- **Adding Columns**: Always add as optional (`?`) or with `@default(...)`.
- **Deleting Columns**: Remove all application references in Release $N$, drop column in Release $N+1$.
- **Renaming Columns**: Add new column, dual-write, backfill, remove old column in separate releases.
- **Indexes**: Create indexes with `CREATE INDEX CONCURRENTLY` or via non-blocking DDL.

## 4. Pre-Migration Backup Protocol

Before any database deployment, an automated backup is created:

### Automated Backup Command:
```bash
pg_dump "$DATABASE_URL" --clean --if-exists --quote-all-identifiers \
  --file="backend/backups/db_pre_migration_$(date +%Y%m%d_%H%M%S).sql"
```

### Verification Script:
Run `bash scripts/verify-db-backup.sh` to verify backup file integrity and retention policy compliance (retention: 30 days).

---

## 5. Emergency Rollback Protocol

If a deployment fails or causes severe runtime regressions post-migration, follow this step-by-step runbook:

### Step 1: Immediate Halted Deployment
Pause CI/CD rollout and route traffic back to the previous stable release container image.

### Step 2: Identify Pre-Migration Snapshot
Locate the latest pre-migration backup file generated by `deploy-migrations.sh`:
```bash
ls -lt backend/backups/db_pre_migration_*.sql | head -n 1
```

### Step 3: Restore Database Snapshot
Execute database restore using `psql` or `pg_restore`:
```bash
psql "$DATABASE_URL" < backend/backups/db_pre_migration_<TIMESTAMP>.sql
```

### Step 4: Resolve Prisma Migration State
Mark failed migration entries as rolled back in Prisma's internal metadata table:
```bash
npx prisma migrate resolve --rolled-back "<FAILED_MIGRATION_NAME>"
```

### Step 5: Post-Rollback Verification
Run system health check:
```bash
npm run test:smoke
```
